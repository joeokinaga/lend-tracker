# 判断の記録

## 2026-11-09 催促は借りた相手にアプリから直接送る

- 決めたこと：貸した記録の通知は、連携済みの借りた相手に公式アカウントから直接プッシュ送信する。相手が未連携のときは、貸した本人に転送用の催促文と招待リンクを送る。
- 理由：差別化は「LINEで完結すること」と「送りづらい催促を自分で送らなくていいこと」。本人が転送する方式では、気まずさが半分しか消えない。
- 検討して採用しなかった案：本人だけに通知し、催促文を本人が転送する方式。実装は簡単だが、差別化ポイントを満たさない。未連携時の代わりの手段としてだけ残す。
- トレードオフ・リスク：相手にも友だち追加とログインをしてもらう必要がある。招待・同意・通知停止・相手側の個人情報の扱いが増え、工数は2〜3日増える見込み。相手の分も通知数の枠を使う。嫌がらせに使われないよう、文面は固定のテンプレートにし、相手が通知を止められるようにする。
- 見直す条件：相手の連携率が低い場合（目安：招待した相手の半分未満）は、招待の流れか代わりの手段を見直す。

## 2026-11-09 期限を過ぎた後は7日ごとに、返却されるまで通知する

- 決めたこと：期限超過日数 d（JSTの日付で数える）が -1、1、3、または「d ≥ 7 かつ d % 7 = 0」の日に通知する。受信者ごとに1日1通にまとめる。「貸し借り × d」の組を送信履歴に記録し、同じ通知を2回送らない。
- 理由：返却されるまで忘れられないようにする。7日までは間隔を短くし、それ以降は週1回にして、うるささを抑える。
- 検討して採用しなかった案：7日後で通知を止める案（返却されないまま放置されやすい）。毎日通知する案（迷惑になり、通知数の枠も足りない）。
- トレードオフ・リスク：返却されない貸し借りでは、通知がずっと続く。Cronが失敗した日の分は、その日の d にしか一致しないため取りこぼす（扱いはフェーズ2の通知ロジックで決める）。
- 見直す条件：月の送信数が枠の80%を超えたとき。相手からうるさいという声が出たとき。

## 2026-11-09 金額は円の整数、返却期限は任意、一部返済は扱わない

- 決めたこと：金額は 1〜10,000,000 の整数（円）。返却期限は任意で、未設定のものは通知しない。一部返済はMVPでは扱わない。
- 理由：整数なら浮動小数の誤差が出ない。期限を決めない貸し借りもある。残高管理まで入れると、DBとUIの複雑さが大きく増える。
- 検討して採用しなかった案：返却期限を必須にする案。外貨に対応する案。
- トレードオフ・リスク：一部だけ返してもらった場合は、メモ欄で代わりにするしかない。
- 見直す条件：一部返済の要望がフィードバックで2件以上出たとき。

## 2026-11-09 構成は Cloudflare Workers（API＋静的アセット）+ D1 + Cron Triggers

- 決めたこと：Workers 1つで Hono API と React SPA を配信し、D1 と Cron Triggers を使う。Pages は使わない。
- 理由：Cron は UTC 0:00（JST 9:00）に設定でき、休止もない。APIと画面が同じドメインになるのでCORSが要らず、デプロイも1回で済む。静的アセットへのリクエストは無料で無制限。
- 検討して採用しなかった案：Vercel Hobby + Supabase（Cron の実行時刻が ±59分ずれる。1週間操作がないとDBが一時停止する）。Pages + 別の Worker（デプロイ先が2つになる）。
- トレードオフ・リスク：CPU は 10 ms/回 まで。SQLite なので、Postgres の機能は使えない。Cron の実行時刻は厳密には保証されていない。
- 見直す条件：CPU の上限で失敗が出たとき。利用者が増えて無料枠を超えそうなとき。

## 2026-11-09 相手との連携は「連絡先」単位にする

- 決めたこと：招待と同意は、貸し借り1件ごとではなく、連絡先（contacts）ごとに行う。
- 理由：同じ相手と何度も貸し借りするとき、招待を1回で済ませるため。
- 検討して採用しなかった案：貸し借りごとに招待する（相手の手間が多い）。
- トレードオフ・リスク：相手が通知を止めると、その貸した人からの通知がすべて止まる。
- 見直す条件：貸し借りごとに止めたいという要望が出たとき。

## 2026-11-09 セッションは IDトークンを1回検証したあと、D1に保存するCookieセッションにする

- 決めたこと：ログインのときに LINE verify API で IDトークンを検証し、ランダムなトークンを発行する（DBにはハッシュを保存し、HttpOnly Cookie で返す）。
- 理由：リクエストごとに LINE へ問い合わせなくて済む。退会やログアウトのときに確実に無効にできる。
- 検討して採用しなかった案：毎回 IDトークンを検証する（遅くなるうえ、トークンの有効期限が1時間しかない）。署名付きJWTだけで管理する（取り消しができない）。
- トレードオフ・リスク：DBへの問い合わせがリクエストごとに1回増える。
- 見直す条件：D1 の読み取りの枠が足りなくなったとき。

## 2026-11-09 削除は物理削除、通知履歴には個人情報を持たせない

- 決めたこと：貸し借り・連絡先・退会は物理削除にする。通知履歴は、内部IDとステータスコードだけを持つ。
- 理由：個人情報を最小限にし、退会時の全削除を簡単かつ確実にするため。
- 検討して採用しなかった案：論理削除（個人情報が残り続け、すべてのクエリに条件を付ける必要がある）。
- トレードオフ・リスク：誤って削除すると元に戻せない（確認ダイアログで防ぐ）。
- 見直す条件：「間違えて消した」というフィードバックが出たとき（そのときは「ゴミ箱」を検討する）。

## 2026-11-09 通知は「計画を保存してから送る」2段階方式と Retry-Key で冪等にする

- 決めたこと：Cron を 3本（JST 9:00 / 9:30 / 10:30）設定する。受け取る人×日、貸し借り×段階の UNIQUE 制約で計画を INSERT OR IGNORE してから送る。push には delivery ごとに固定の X-Line-Retry-Key を付ける。過去の分はさかのぼって送らない。送る前に、今月の残りの通数を確認する。
- 理由：DB と LINE の両方で二重送信を防ぎつつ、一時的な失敗は再送で拾うため。
- 検討して採用しなかった案：送ったあとで記録する（記録の前に落ちると二重送信になる）。Queues を使う（構成が大きくなる）。
- トレードオフ・リスク：Cron が丸1日失敗すると、その日の通知は届かない。
- 見直す条件：取りこぼしが実際に起きたとき。

## 2026-11-09 パッケージ構成は単一パッケージ、npm を使う

- 決めたこと：`src/server`・`src/client`・`src/shared` を1つのパッケージに置く。`@cloudflare/vite-plugin` で画面と Worker を一緒にビルドする。パッケージマネージャーは npm、Node は 24（`.nvmrc`）。
- 理由：2〜5人向けの規模では、モノレポにする利点より設定の手間のほうが大きい。npm ならツールを増やさずに済む。
- 検討して採用しなかった案：pnpm workspaces（apps/web・apps/api・packages/shared の3つ）。
- トレードオフ・リスク：フロントとサーバーの依存関係が1つの package.json に混ざる。
- 見直す条件：品物の機能や管理画面を追加して、規模が大きくなったとき。

## 2026-11-09 E2E ではテスト用の認証を使い、本番では無効にする

- 決めたこと：`AUTH_TEST_MODE=1` のときだけ `/api/test/login` を有効にする。本番の環境では、この値が入っていたら起動に失敗させる。
- 理由：CI では LINE に実際にログインできないため。
- 検討して採用しなかった案：LIFF をモックして IDトークンを偽造する（サーバー側の検証をすり抜ける仕組みが必要になり、かえって危ない）。
- トレードオフ・リスク：設定を間違えると、認証を回避されるおそれがある（起動時のチェックとテストで防ぐ）。
- 見直す条件：なし。
